# Provider request status and recovery

A newly submitted request is recorded with its operation ID before dispatch. While the current tab is actively processing that request, the interface shows normal progress rather than an unconfirmed-request warning. If a request fails, its outcome is uncertain, or the page is reopened with a retained receipt, the original operation remains available for inspection. Check its original result before authorizing a separate request; a separate provider request can incur another charge. A proven absent or claimed operation may be retried using the original identity according to the existing server checks.

The production architecture intentionally uses one MySQL database on Server 2. A single-copy response is the expected topology and does not trigger a degraded-mode banner. Genuine provider, storage, or unresolved-operation warnings remain visible. Historical copies of the obsolete single-copy warning are suppressed in the interface without deleting conversation data.

This change affects browser status presentation only. It does not change request deduplication, account ownership, provider dispatch, database durability, file storage, or backup policy. The deployed WAR preserves the existing server classes and replaces only the reviewed browser assets and their bundled call-source copies. Both application servers must serve the same release. Server 2's monitor capacity-proof artifact hashes must be rebound to the new WAR during deployment while preserving its existing safety thresholds. A database outage blocks database-dependent operations; there is no automatic database failover.
