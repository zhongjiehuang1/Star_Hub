# Atomic two-member storage (current candidate, 12 November 2026)

Production writers require `storage.replicated=true`, `storage.transactionMode=atomic`, the explicit physical membership `1,2`, and migrations 007 through 013 (gate protocol 5). In atomic mode a peer Tomcat outage does not invalidate a healthy peer MySQL/GR/capacity participant; the surviving local Tomcat must still pass its own application gate. Entrance forwarding and this distinction need real outage validation. Both physical servers hold the complete account schema and both logical BLOB schemas, replicated by MySQL 26.10 Group Replication in multi-primary mode. Either application may accept writes. The old single-coordinator XA design below is historical; legacy recovery is now permitted only for explicitly named disposable test schemas on loopback. It is not a production fallback.

The deployed private capacity endpoints are exactly `http://127.0.0.1:941/status` for physical node 1 and `http://127.0.0.1:942/status` for node 2, reached through the existing private tunnels where necessary. All configured endpoints are validated before any bearer is sent; duplicate mappings, extra nodes, host aliases, other ports/paths, user information, queries, fragments and HTTPS/remote substitutions are rejected. The private HTTP client explicitly bypasses proxies and never follows redirects. A later port or transport migration requires a reviewed code/configuration change; it is not an automatic fallback.

Every account, conversation, key, payload-segment and publication transaction updates the same InnoDB certification gate in its local commit. Local row locks alone do not coordinate separate MySQL members; a competing certified gate update produces a known transaction rollback, retried at most three times. DDL, transaction-control SQL, session SQL and JDBC connection escapes are rejected on borrowed application connections. Runtime credentials need DML on both logical schemas and read-only access to the drained legacy decision identity. Cascading foreign keys must be migrated to RESTRICT while all writers are fenced. Startup rejects a non-drained legacy journal or inconsistent pending quota. New application SQL sessions explicitly select UTC; existing TIMESTAMP values are retained.

Before a transaction, the app obtains a controller permit bound to the MySQL UUID, controller boot, durable grant, member view, membership and dual/single mode. It checks the identical permit immediately before commit. After commit it reads the GTID set on that connection and asks the real controller to confirm application and persistence on the required members. The client validates an exact loopback observer URL, disables proxies and redirects, and requires all seven confirmation lease headers plus durability to match the captured grant. Only then may the buffered HTTP success and deferred session changes be returned. A changed permit, lost commit reply or failed confirmation produces an unknown outcome with the original operation ID. Replaying an already recorded result also requires a fresh confirmed transaction. Single mode is explicitly reported by `X-Four-Project-Durability: single`; it has one durable copy until controlled rejoin.

Login failures and password-change failures are also durable outcomes. Login budgets are shared per HMAC client identity; password-change budgets are shared per HMAC account/generation across physical nodes, browser sessions and client addresses. Each random operation UUID is bound to its complete request, and replay never increments the failure count again. Eight wrong current-password attempts block another guess for the current fifteen-minute window. Existing password validation, current SQL password-hash checks and generation checks remain required; a status receipt cannot grant authentication. Password-change responses preserve the existing 403 for a wrong current password and 429 for the shared limit, with a matching COMMITTED receipt only after confirmation. Invalid new-password syntax returns a confirmed 400 receipt without counting a password guess. A changed password committed without acknowledgement invalidates the old session hash; users must authenticate with the current password before querying/replaying the saved result.

The account browser refuses a new mutation if it cannot save and read back its opaque operation UUID in this tab's session storage. An already retained in-memory uncertain UUID may still be queried or retried unchanged during a storage failure. It retires a pending UUID only after matching `operationId`, `operationState: COMMITTED` and current dual/single durability, or a separately confirmed original-result query. Workspace requests capture their account before hashing and reject an account change before any dispatch or response application. Editing an uncertain payload does not silently obtain a new UUID. Tester-region verification retains its existing token/origin/password policy and immutable replicated session attributes; its entrance limit is per IP per Nginx entrance (five requests per minute plus burst five), not a durable cluster-wide failure budget. It must not be described as a global lockout.

## Shared memory admission and storage refusals

Provider run/chat/check/batch, full provider-result queries, binary media/import, guest operations and account/workspace heavy requests share one public heavy-task slot per webapp JVM. Provider handlers acquire before reading their bodies. Other handlers read at most 16 KiB plus one byte before acquiring, and acquire before completing a large body, accessing a session, performing SQL or expanding a large result. A busy handler returns 429 without claiming or dispatching an external operation, changing quota, or acknowledging success. It never substitutes a new operation UUID. Internal helper calls inside an admitted provider task do not acquire again. Each of the two physical JVMs has its own slot and remains an equal database writer; this bounds memory rather than choosing a permanent primary. Actual two-entry convergence, maximum heap, streaming timeouts and response disconnects still require deployment measurements.

Only strict <=16 KiB fixed status requests can bypass this slot: account `loginStatus`, and the optional workspace `operationSummary` with exactly action, operationId and expectedEmail fields. Summary verifies current account/generation and returns only operationId, state, kind and logicalBytes. It does not read file lists, request receipts or content. Existing `operationStatus`, `requestStatus`, `readFile`, `listChats`, guest data/status and provider-result queries keep the slot because their responses can be large.

New generic mutation acknowledgement rows are limited to 16 KiB of response bytes. Public chat/file/guest/provider limits remain unchanged. Existing larger committed receipts remain available through their original bound result query and exact retry; they are not reclassified as new writes. Save/deleteChat reads the actual old UTF-8 payload/title lengths and admits their FULL row-image cost, the new content where relevant, and the bounded receipt before changing data. Historical chat rows above this current bound remain readable and receive an explicit migration-required refusal on mutation. Uncalibrated legacy inline file trash/restore and legacy BLOB/inline permanent deletion likewise preserve bytes and quota until independently calibrated migration.

An exact capacity refusal is HTTP507 with code `INSUFFICIENT_STORAGE`, the original operationId and operationState UNKNOWN, without a durability-success header. Earlier segments or the original reservation may already be committed. Query, retry or explicitly cancel using that original ID; a507 is never proof of rollback and never triggers timeout cleanup. Cancellation/deletion rechecks remaining cleanup/log allocation before each bounded deletion and keeps reservations until confirmed completion. The 4,000,000,000-byte safety floor is unchanged and is not enlarged by these operation forecasts.

## Bounded immutable payload storage (protocol 5)

New files, guest values and provider results use the same immutable `starhub_payload_manifests` and `starhub_payload_chunks` tables. A row contains at most 2 MiB of plaintext file content or authenticated ciphertext. Owner/generation, operation UUID, request binding, exact length, segment count, each segment SHA-256 and the complete payload SHA-256 are checked. Retrying the same segment compares its actual bytes and digest; it never overwrites an existing row. Each stage is a separate real authority-bound transaction and confirmation. READY requires every expected index and the complete digest; a small publication transaction changes the business reference, relevant budget and terminal receipt atomically. A segment is not a publicly readable file or completed model response merely because it exists.

A transaction-level guard counts actual inserted/deleted segment bytes across nested helper calls, with a 3 MiB aggregate ceiling; each segment remains at most 2 MiB. The separate maximum competing-mutation cost is 6,019,274 bytes: actual old plus new bounded conversation UTF-8/title images and the maximum new acknowledgement row can exceed the 3 MiB segment-mutation ceiling. File, provider and guest physical admission includes that larger competing cost. This number is a payload/image cost, not a promise that every SQL transaction has only that many encoded bytes; metadata and logs also require measured amplification. Most staging steps change one segment. A real one-MiB guest snapshot can require two segment rows because ciphertext includes a nonce and authentication tag; its combined values are published atomically through field selectors. This does not lower the 12 MiB image, 64 MiB logical save batch or 12,000,000-code-unit guest-field limits.

Files retain their separately confirmed fixed-ID reservation until all segments have been checked and one small transaction publishes the entire catalogue batch. A cancellation first durably changes RESERVED to CANCELLING. No later stage or publication may pass that parent-state check. Cleanup deletes bounded segments in separately confirmed transactions, retaining logical/physical reservations until the final CANCELLED transition. A committed file is never deleted by an older cancel. Deleting an already trashed file similarly records DELETING, prevents restoration while cleanup is in progress, and keeps its charged usage until every segment is gone. A newly authorized node can continue the original operation and fixed IDs without guessing that an old JVM has died.

Guest browser chunks remain at most 100,000 code units. Each becomes a bounded encrypted immutable payload; a committed field is a small ordered manifest, so appending or committing does not copy a growing 24 MB encrypted BLOB. Field snapshots and stream cursors carry versions and original transaction identities. Replaced streams/fields enter a persistent cleanup queue. Shared payload reference counts distinguish live fields, staging and cleanup, and cleanup verifies both the count and actual live manifests before deleting. Retired versions remain charged until their actual payloads have been cleaned. No expiry or tab closure erases uncertain receipts or releases a budget. Existing inline guest rows are read-only compatibility data; a large legacy value or unresolved legacy stream requires a reviewed migration, not an online large-BLOB UPDATE/DELETE. The actual two isolated primary schemas were checked to contain zero old guest field/staging rows before the candidate migration.

Provider completion first persists an immutable encrypted result intent bound to the original dispatch ticket. It stages at most 32 MiB of serialized result, then publishes COMPLETED or COMPLETED_NO_RESULT and releases its reservation in one small transaction. A different result cannot replace that intent. A new JVM querying an owner-authorized operation may verify and publish a complete staged result even if the old JVM crashed before sealing or responding. A partial result remains SENT/UNKNOWN and does not authorize another provider dispatch. The old inline result column is read-only compatibility data; neither the outer HTTP wrapper nor guest operation receipts duplicate the large result. Guest receipts have an explicit 16 KiB status-only bound.

Physical accounting uses actual free space for already retained/staged bytes and reserves future work separately. A file reservation covers the greater of finishing the remaining segments and explicitly cancelling the existing segments; CANCELLING/DELETING covers remaining deletion work. Provider result reservation shrinks from its maximum to the immutable result plan minus materialized bytes. Guest staging/retired payloads also contribute future cleanup cost to shared admission. Every segment updates its remaining reservation in the same commit. The exact free-space floor remains 4,000,000,000 bytes. The model factor and fixed operational cost must be measured again for these bounded transactions, HTTP spool, metadata, rollback, deletion and concurrent operations; the previous unvalidated fixed constant is not a second floor or a validated allowance. Capacity validation remains closed until that real evidence exists.

Startup audits a consistent read snapshot of payload lengths/indexes/states, business parents, ownership and guest reference counts, with fresh controller grant checks before/after. It preserves partial intents and tombstones. It does not treat a timeout, missing response, process-local lock or cached health flag as a rollback or proof of peer fencing.

## Durable upload reservations

Ordinary files retain their 4 MiB limit; generated images retain 12 MiB per image with an explicit 64 MiB total save-batch limit. The account quota is exactly 2,000,000,000 bytes, including trash, durable pending uploads and concurrent reservations.

1. The browser hashes the complete file, keeps a stable UUID in session storage, and sends `reserveUpload` with its name, MIME type, length and SHA-256. A small separately confirmed transaction assigns fixed file IDs, records the request binding and controller epoch for audit, and charges logical and physical reservations. No content is sent before reservation confirmation.
2. `upload` must present that same operation and exact payload. Any currently authorized node can fulfill the reservation. Real immutable content segments are individually staged and confirmed. One final small local transaction publishes all file metadata, transfers reserved quota to used quota, releases physical budgets, and records COMMITTED. GR replicates every segment and related row; no partial batch becomes a public library file.
3. A different view requires explicit re-confirmation of the same reservation before content. The quota is not charged twice and file IDs do not change. Lost reservation or content responses retain the original UUID. Query `operationStatus` or retry the original operation; unknown is never presumed to mean rollback.
4. The library reports `storedBytes`, `reservedBytes`, `used` (their sum), and paginated `pendingUploads`. Explicit `cancelUpload` competes with completion in the same gate/operation transaction. CANCELLED cannot reopen; cancellation of COMMITTED is idempotent and keeps its bytes. There is no timeout, orphan scan or presumed-dead owner release. A pending reservation remains visible until the user continues or cancels it.

Each physical process admits at most one file mutation at a time. Durable shared reservations account for remaining payload/log/temp work on every active physical member, guest cleanup, and another simultaneous bounded segment operation. The capacity model must be measured, marked validated, and enforced by the controller before readiness is allowed. The only safety floor is 4,000,000,000 bytes, with minimal filesystem block rounding. Physical write budgets are explicit costs, not another hidden floor. Pending physical budgets remain durable until a terminal result. Unrestricted privileged writes can consume filesystem reserved blocks; filesystem reserve and application admission do not claim protection against arbitrary root activity.

## Guest sessions and cross-JVM concurrency

Guest conversations, packed attachments, provider keys and pending uploads use encrypted common payload segments plus guest metadata in the account schema. Migration 010 introduced budget/session/tab/receipt tables and the retained legacy inline field/staging tables. Migration 013 adds `starhub_guest_values`, `starhub_guest_streams`, `starhub_guest_cleanup` and `starhub_guest_payload_refs`; migration 012 supplies common payload headers and segments. The same tables are required in the disposable worker-primary schema; the logical peer BLOB schema and the legacy decision schemas are unchanged. Migration 010 introduced protocol 3. The current candidate advances to protocol 5 and rejects older WARs before admitting writes. Runtime accounts receive exact table-level privileges: immutable segment rows cannot be updated and header tombstones cannot be deleted. No new administrative privilege is given to applications.

Tomcat's replicated HttpSession holds only a random guest identity String. First creation uses a shared-secret HMAC of the server's logical session cookie as a unique SQL lookup, so concurrent JVMs or a lost initial commit response recover the same identity. A Tomcat route suffix does not create another logical identity. The browser cannot select an old identity by supplying a UUID. Tomcat session replication and synchronous acknowledgements still need actual deployment acceptance; the application does not treat them as a cross-JVM mutex. Region verification, CSRF/origin protections and guest/account isolation remain in place.

Each begin/chunk/commit/snapshot/renew has a stable UUID derived from its tab, transaction, action and chunk index and a secret HMAC binding to the complete request. Its encrypted result is recorded in the same certified SQL commit. A retry with different contents is rejected; completed retries do not append or charge again. `status` with the original operation ID reports its committed phase receipt or UNKNOWN, never a timeout-based rollback. The browser keeps the same transaction ID when a chunk or renewal response is uncertain. A delayed older begin cannot erase a higher staged version, and same-version concurrent changes return a conflict instead of silently replacing data. Staged bytes are charged but remain invisible until a valid JSON commit.

AES-GCM protects values, staging and receipts using the private shared vault key and AAD bound to the guest, tab, field, version, transaction and purpose. Packed attachments can contain lone UTF-16 surrogates, so encryption preserves exact 16-bit code units instead of using a lossy charset encoder. The inherited guest bounds are explicitly code-unit bounds: 12,000,000 per field, 24,000,000 per session including staging, and 64,000,000 across the cluster. These correspond to up to 24/48/128 MB of plaintext code units, plus encryption, row and log overhead; they are not a claim about JVM heap usage. The database maintains these counters transactionally. Sessions, tabs and operation receipts also have explicit count limits. No process-local static total is treated as a cluster budget.

Before a guest write, physical admission includes current durable file/provider reservations, retained staging/cleanup work, the incoming bounded guest mutation and another concurrent bounded segment. A field commit switches only small manifests; a rewrite retains and charges old segments until bounded cleanup completes. Admission keeps the same exact 4 GB floor. Real MySQL growth, temporary memory, HTTP spooling and insertion/deletion binlog cost must be measured before the physical model is accepted.

The guest lease has a ten-minute idle access limit. An expired lease rejects ordinary requests; an explicit, idempotent renewal is allowed only through the still-valid server-side Tomcat session and retains pending bytes and all receipts. A genuinely expired Tomcat session creates a new identity and cannot access the previous namespace. Closing a browser tab or expiring access does not physically erase encrypted SQL rows. There is no automatic TTL cleanup or presumed-abort scan: encrypted state and receipts remain until coordinated maintenance. Operators must not delete pending/uncertain state to free space. When a configured count or logical/physical budget is exhausted, requests fail safely and the browser retains its current data; maintenance is required before new capacity is promised.

The internal recovery probe now uses actual runtime JDBC credentials and fresh authority checks before/after read-only queries of the gate, identity and critical account/file/guest tables. It does not update the certification gate or depend on its own `/ready` result. A dropped table, changed identity, unavailable database or changed authority fails the probe. This avoids readiness loops and avoids turning frequent probes into competing multi-primary write transactions.

## Durable provider-operation receipts

Migration 011 adds `starhub_provider_operations` and `starhub_provider_capacity` to each account/worker-primary schema and raises the intermediate gate to protocol 4; migrations 012–013 supply the current bounded protocol 5. Each HTTP model, search, batch or connection-check request needs a random `operationId`, the current server-session owner, `ownerTab` and `expectedEmail`. A shared-secret HMAC binds the complete request, including its API key, without retaining plaintext credentials. The API records and confirms CLAIMED, then separately records and confirms SENT before any external dispatch. A one-use, in-memory dispatch ticket checks its original controller grant again immediately before each actual HTTP call, including search followed by generation and batch file upload followed by job creation.

`POST /api/provider-operation` queries the original UUID through a newly authorized and confirmed transaction. ABSENT and CLAIMED permit retrying the original request and UUID. SENT and UNKNOWN never authorize another provider call. A crash after SENT but before a call may therefore leave an operation unresolved even when the provider did nothing; this deliberately avoids inferring that an uncertain paid effect can be repeated. There is no automatic timeout release, receipt deletion or provider retry. A separate, explicit new intent may incur another charge. The implementation does not claim exactly-once delivery to an external provider that offers no verified idempotency/result-query contract.

COMPLETED receipts retain an AES-GCM-encrypted result, bounded at 32 MiB serialized per operation. Account image receipts retain quota-counted library file IDs instead of another copy of image bytes; replay hydrates only files the current owner may still read. An image that could not be saved, or an oversized result, leaves explicit COMPLETED_NO_RESULT metadata and never reruns the external call. Guest provider receipts have this independent bound in addition to the guest-field code-unit budget. Durable physical reservations share the file/guest accounting totals and are released only by a confirmed terminal transition. Record-count and active-operation limits reject further work safely rather than removing uncertain receipts.

Streaming deltas are partial, unconfirmed output. The terminal SSE `done` carries the matching UUID, terminal state and actual dual/single durability only after the result commit is confirmed; it omits the already streamed text/reasoning to keep one event bounded. The browser retains an empty result placeholder containing the UUID and does not retire that UUID until the result is displayed and the corresponding account conversation or guest snapshot has separately received durable confirmation. Browser persistent storage contains request identities, state and fingerprints, not frozen prompts or API keys.

A realtime WebSocket connect has its own durable SENT ticket. The live relay rechecks its grant periodically and before non-audio control events; queued audio is not persisted per frame and cannot be recovered or replayed after a crash. Closing the local relay records local completion metadata only, including the fact that provider billing may continue. Uncertain disconnects retain UNKNOWN/SENT. Reusing an old UUID cannot open another provider socket. Tomcat session replication and actual browser forwarding remain deployment acceptance requirements.

Every Tomcat and real provider-validation JVM must start with these individual options before any HTTP-client class is initialized:

```text
-Dsun.net.http.retryPost=false
-Djdk.httpclient.disableRetryConnect=true
-Djdk.httpclient.enableAllMethodRetry=false
-Djdk.httpclient.redirects.retrylimit=1
```

The application verifies actual JVM startup arguments and current properties before accepting a provider claim. A late `System.setProperty` is insufficient. Redirects are disabled, provider POST bodies use fixed-length streaming, and GET/WebSocket transports have a single total attempt. Header/content HTTP debugging and disabled hostname verification are rejected. These flags follow the [JDK 21 networking-property contract](https://docs.oracle.com/en/java/javase/21/docs/api/java.net.http/module-summary.html) and the [OpenJDK request-attempt implementation](https://github.com/openjdk/jdk21u/blob/master/src/java.net.http/share/classes/jdk/internal/net/http/MultiExchange.java). Local loopback tests count requests after dropped POST/GET/WebSocket responses, redirects, oversize bodies and stalled bodies. Deployment must repeat these on the actual JDK; they do not replace real controller/MySQL unknown-result tests or paid-provider acceptance.

Apply 011–013 only through the reviewed online-GR migration procedure: both actual members ONLINE PRIMARY, BEFORE_AND_AFTER consistency, stable real dual controller grant, application writers and public entries stopped, and binary logging enabled on the canonical writer. Let GR create identical tables on the peer; do not initialize or independently seed the peer. Verify original non-gate tables unchanged, both gate markers 5, actual table checksums and final dual GTID confirmation before staging the matching WAR. A partial migration leaves writers closed for inspection.

## Current validation and real fault harness

Local SQL tests use H2 and explicitly simulated authority/GTID/capacity adapters. They verify local atomicity, binding, pending quota, cancel/content competition, unknown outcomes, JDBC guards and HTTP buffering; they do not establish real cross-host GR durability or failover. Keep formal writes closed until real MySQL 26.10, Tomcat 11, dual-host networking, capacity, fencing and controlled-rejoin acceptance succeeds. Historical test counts below must not be treated as current acceptance.

`com.starhub.AtomicStorageValidation` in test classes refuses business schemas and non-loopback URLs. It uses the private worker configuration, real Connector/J and real controller endpoints. The parent deployment run supplies the exact runtime classpath and private paths; no secret belongs in a command argument. The phases are:

- `basic`: both synthetic users and ingress identities, random full-byte readback, replay/conflict, account isolation, delayed trash retry, restore and deletion.
- `upload OPERATION_UUID USER_ID BYTES SEED` and `batch ...`: bounded incompressible payloads up to the configured 64 MiB batch.
- `hold OPERATION_UUID USER_ID BYTES SEED PAUSE_MILLIS`: confirms the reservation and each content segment first, opens the final small publication transaction, prints `READY_BEFORE_COMMIT`, pauses at most 120 seconds, then commits and confirms publication.
- `after-commit OPERATION_UUID USER_ID BYTES SEED /var/lib/codex-validation/RELEASE_FILE`: confirms the reservation and content stages first, physically commits final publication, prints `READY_AFTER_LOCAL_COMMIT`, waits at most 120 seconds for the dedicated release file, then asks the real controller to confirm. This test-only connection barrier permits an external JVM/MySQL stop between local commit and confirmation without substituting a fake GTID or durability response.
- `status OPERATION_UUID USER_ID`: queries the original operation through a newly confirmed transaction.
- `capacity`: alternates two real synthetic users towards exactly 2,000,000,000 bytes each, reads every file back, checks the actual filesystem floor, and reports safe 507 refusal if physical capacity cannot fit. It leaves its disposable test state available for inspection.
- `guest-write`, `guest-read`, `guest-status RUN_UUID VERSION UNITS SEED`: real encrypted shared-guest writes, exact readback and original-operation queries. `guest-cleanup` explicitly continues already authorized retired-payload cleanup. Maximum writes use the real begin/chunk/commit protocol, rather than an internal snapshot larger than the HTTP limit. `guest-hold` and `guest-after-commit` add a private release-file barrier before commit or after the physical local commit. Units are bounded to fit one existing guest field; no timeout clears staged state.
- `provider-claim`, `provider-run`, `provider-max`, `provider-status OPERATION_UUID SEED`: real controller/JDBC claims, dispatch receipts and encrypted result queries. `provider-max` stages a serialized result at the unchanged 32 MiB limit and prints only size/digest metadata. The only external-effect substitute is an explicitly printed `SYNTHETIC_EFFECT_ONLY` marker, never a network request or paid API. `provider-hold-sent`, `provider-after-local-sent`, `provider-after-effect`, and `provider-after-local-result` add a private release-file barrier at the named point. Killing a worker must not make another JVM repeat that marker after SENT; replay after a confirmed result returns its stored payload. Use the four JVM options above. These synthetic phases test the database/authority boundary, not a manufacturer's billing API.

Do not use the harness on business data. `initialize` may only create empty disposable schemas; the deployment normally seeds both servers from one verified canonical clone so UUID identities match. Never initialize both independently, replace a marker, remove an unresolved reservation, or enable legacy recovery to get past readiness.

# Distributed file storage deployment

**11 November 2026 status:** The instructions below describe the retained legacy coordinator/XA design and experimental replication hooks, not an accepted two-equal-writer production deployment. Current source uses Jakarta APIs for Tomcat 11 and Connector/J 26.10.0. The 2 GB quota and 4 GB floor are source-level rules; real MySQL 26.10, disk enforcement, full file replication, fencing and failover still require deployment validation. Historical results do not certify the current system.

This release requires Java 17 or later, MySQL 8/InnoDB, and one active StarHub coordinator. It does not enable automatic coordinator failover. Node 1 owns account/chat/key metadata, file catalogue, quota, durable operation journal and reservation rows. Immutable file bodies can live on node 1 or node 2. Existing inline file bodies remain readable; new bodies use `file_blobs` and an explicit `storage_node_id`.

## Configuration and deployment order

1. Stop every account/file writer and take verified database and durable transaction-store backups. Persist `binlog_format=ROW` on both MySQL servers, change the live global setting during the maintenance window, and restart/drain application connection pools so every new connection uses ROW. Migration 004 sets its own session to ROW and requires the maintenance privilege to do so; changing only that session does not establish the runtime prerequisite. Preserve UUIDs and user generation values. Apply existing account/workspace migrations, `003_file_pagination.sql`, and `004_distributed_file_storage.sql` to the primary database. Apply `005_file_blob_node.sql` to both body databases. Verify no orphan owner rows remain. Existing login sessions must authenticate again because sessions now include the immutable user generation.
2. Create a private persistent transaction-store directory owned by Tomcat, outside the WAR and temporary deployment directories. Provision its `identity` file from the single `file_storage_coordinator.store_identity` value while writers remain stopped. An existing identity must match; never generate a replacement to bypass a mismatch. Keep directory/file permissions restrictive. Never delete or replace this store, its decisions, or operation/receipt rows to make recovery succeed.
3. Configure the private `account-config.properties` using [the example](../deploy/distributed-storage.example.properties). Node 1 alone sets `storage.coordinator=true`; node 2 keeps it false. Database credentials and tokens stay outside source, the WAR and logs. Give application accounts only required schema privileges and the MySQL `XA_RECOVER_ADMIN` privilege required to enumerate their XA branches. Keep MySQL inaccessible from the public network.
4. Run authenticated private node probes, validate the physical storage boundary described below, and establish encrypted private tunnels for node 2 MySQL/probe access. Both probes must report real database and basic Tomcat readiness. Do not probe coordinator readiness from a probe that the coordinator itself needs: that creates a startup cycle.
5. Both Nginx entrances must overwrite `X-Starhub-Ingress-Node` with their fixed 1/2 identity and `X-Starhub-Ingress-Token` with the deployment secret. Strip user-supplied values. All stateful StarHub requests, including guest/session/region-gate/WebSocket requests that depend on the same session, must route to the one coordinator and preserve cookies and trusted original client address. `GET /api/server` stays local so its badge identifies the entrance. Static files and independent public metadata may remain local.
6. Block public access to `/api/internal/*`. Verify the private authenticated recovery endpoint, the public cluster-health endpoint, upload/read/trash/restore/delete, retries and cross-node file placement before opening writes. Deploy both WARs from the same build. An edge node must not directly service account requests against its own database.

The old single-server deployment helper does not set up this contract and must not be treated as sufficient for the dual-node release.

## Health and failure behavior

- `GET /api/server`: `{ "serverId": 1 }` or 2, no-store; missing/invalid deployment ID returns 503.
- `GET /api/cluster-health`: only `{ "status": "ready" }` (200) or `{ "status": "unavailable" }` (503). No host, region or address is exposed.
- `GET /api/internal/recovery-ready`: authenticated with the probe Bearer token; 204 only after local coordinator recovery is complete, otherwise 503. This endpoint does not call the probes again.
- `GET /api/health`: basic process readiness, independent of database/recovery; suitable for the node agent's Tomcat probe.

Either required server, MySQL or Tomcat becoming unavailable closes account/workspace operations with `CLUSTER_UNAVAILABLE` and `服务器故障，请等待恢复`. A transaction whose result is uncertain returns `OPERATION_PENDING` with the same message. Static frontend content can still be served. Provider outages are not mislabeled as cluster outages. Guest AI can remain independent; paid requests are never retried automatically.

The coordinator persists admission, user gates and reservations before beginning XA. Narayana alone owns prepare/commit/rollback decisions and durable recovery. Each participant writes a receipt inside the same XA transaction. The user gate is released only after all commit receipts or confirmed rollback of every recorded branch. A process death, missing response or timeout never releases a gate. If Tomcat starts before MySQL, a lifecycle-owned initializer retries every 5 seconds; a running coordinator is never replaced, and shutdown prevents a late constructor from publishing a new coordinator. Recovery requires both required nodes, retains unresolved decision logs, and checks the live transaction table before presumed abort. The transaction store is protected by an exclusive process lock; shutdown retains that lock if requests cannot drain safely. A second coordinator on another host is prohibited without external fencing and ownership consensus.

## Capacity and quota contract

The quota is exactly 2,000,000,000 logical file bytes per user across both body nodes, including trash and generated files. In-flight uploads reserve quota. Existing 4 MiB upload and 12 MiB generated-image limits remain. Upload/import/generated-image paths all use the same storage coordinator. File lists use bounded pagination instead of truncating at 5000.

An optional `storage.replicated=true` development mode reserves upload space on
both physical replicas and requires the JDBC decision-store backend. In this
mode the existing `primary_physical_bytes` operation field records the other
physical replica's reservation; old operation records remain compatible. Both
health probes are required during normal two-node operation. A single-node
reservation is permitted only when the authenticated local node agent reports
that the peer has been fenced and the current database view has been explicitly
authorized. That report relies on an operator verifying the fencing; it does
not independently prove the peer is off. This development mode does not
provide failover by itself. Do not enable it in production until replication,
fencing, recovery, routing and the complete deployment have been validated.
Replicated mode admits one file-library request at a time per active
coordinator to bound memory pressure. A concurrent request receives a
retryable pending response; uploads and deletes must retain their operation ID.

The optional decision-store backend is selected with
`storage.objectStore.backend=jdbc` and private `storage.objectStore.jdbc.url`,
`.user`, and `.password` settings. Its table and identity binding require
explicit stopped-writer maintenance using `starhub-jdbc-decision-store.sql`;
the runtime does not create or drop either table. The binding must match the
existing coordinator identity, and legacy file decisions must be recovered
before a backend change. JDBC storage by itself does not fence a former
coordinator or guarantee database replication.

A disposable cross-host MySQL Group Replication rehearsal interrupted an
upload after a branch commit, fenced the scratch primary, and recovered the
decision and exact file bytes on the surviving scratch member. The application
capacity and health probes in that test were simulated. It did not exercise a
whole-server outage, public routing, real filesystem limits, or the production
deployment.

A private node agent serves `GET /status` with `Authorization: Bearer <storage.probe.token>` and this JSON shape:

```json
{
  "nodeId": 1,
  "observedAtMillis": 1794140000000,
  "mysqlReady": true,
  "tomcatReady": true,
  "replicationMode": "dual",
  "singleNodeAuthorized": false,
  "reserveGuaranteed": false,
  "volumes": [{"id": "mysql-data-and-log", "availableBytes": 50000000000}],
  "physicalBytesPerPayloadByte": 8,
  "fixedOverheadBytes": 8388608
}
```

The numbers above illustrate the protocol only. The agent must derive current capacity and validated upper bounds, not copy sample values. A sample older than 5 seconds or unhealthy node is rejected. `reserveGuaranteed` must stay false until infrastructure enforcement is verified. Report every volume used by the MySQL data, undo/redo, binlog, temporary files and control journal. `availableBytes` means total free bytes before subtracting the required 4,000,000,000-byte floor. Do not subtract this floor a second time from filesystem user-available bytes. For an ext4 volume whose reserved blocks implement this same floor, report total free blocks and account for pending write budgets once. Filesystem block rounding is the only permitted excess in the floor. Physical payload, database, log and temporary-file growth are write budgets, not an additional safety reserve.

In replicated mode, the authenticated local agent must also report a `dual`
view, or a `single` view with the operator fence attestation. Successful account
and workspace responses recheck that view before their first response byte.
If it is unavailable after a commit, the response is an uncertain failure.
Operations with an identity must be resolved or retried using that identity;
other account changes require checking their resulting state before retrying.
These checks complement, but do not replace, database-level fencing and
migration validation.

The application serializes admission on node reservation rows, refreshes probes while those locks are held, and subtracts pending physical budgets before selecting a node. The preferred node is the authenticated ingress; the other node is tried only before admission. The physical budget includes payload amplification and a fixed maximum write burst. `fixedOverheadBytes` must cover the worst configured batch's metadata, quota, operation journal, receipts and bounded logging. A remote body also reserves primary control-metadata headroom. If primary metadata itself cannot safely fit, the operation is rejected even if the other body node has space. An uncertain admitted upload is never moved to another node.

Account deletion remains a maintenance action: first remove its files through the coordinator and confirm all operations for that user generation are terminal before deleting its identity/quota rows. Never reuse a previous user generation.

A free-space sample and XA do not make filesystem space transactional. A strict 4 GB reserve needs infrastructure enforcement: dedicated volumes or a shared capacity authority for all relevant writers, enforced reserved blocks/quotas and bounded log/temp amplification. Unrestricted root writes, backups or other applications can defeat an application-only check. Do not claim protection against them unless their capacity is also controlled. If root-reserved filesystem blocks enforce the boundary for non-root MySQL/Tomcat, state that scope explicitly and prevent unbounded root log/backup growth. A full disk can still cause a transaction to fail; fail-closed recovery must retain its gate until the result is established.

## Idempotency and recovery acceptance

Workspace upload and permanent delete require a client UUID `operationId`. Matching retries return the original result; reuse with a different request or user generation is rejected. The browser preserves pending operation IDs through network/pending responses. A completed new upload receives a new operation ID. Generated-image saves use a separate storage operation ID; no automatic replay of the paid generation request occurs.

Automated evidence in this release includes local Java and browser tests plus an explicit isolated MySQL harness `MySqlStorageValidation`. The harness refuses production database names and uses simulated capacity probes clearly labeled as such. It checks placement, integrity, quota, idempotency, safe fallback, trash/restore/delete, process death during phase two, loss of commit acknowledgement, and process death after prepare before the global decision. The real MySQL test schemas were on one MySQL host; cross-host transport and actual filesystem protections require deployment validation. Do not infer power-loss or full-disk certification from simulated probes.

Never remove pending XA records manually to reopen the frontend. Restore the failed service, preserve the original store, let recovery converge, then verify no pending operation, active user gate, physical/quota reservation or non-live decision remains. If durable journal media is lost or outcomes conflict, remain unavailable and recover from a consistent backup/incident procedure.

## Verification on 8 November 2026

The complete build passed 80 Java tests and 16 browser JavaScript tests, with one existing GeoIP-dependent Java test skipped. Additional real MySQL tests covered ordinary commit/rollback, concurrent competition for the last quota byte, body placement, exact content hashes, primary metadata headroom, idempotent replay, process death after prepare, phase-two process death and lost commit acknowledgement. A separate eligible-orphan recovery test preserved another application's real prepared XID across three scans without attempting a terminal action.

Migration rehearsal imported consistent production snapshots into uniquely named temporary databases. Every original field and full row projection remained identical across 17 finance tables and five StarHub tables, and repeated migrations preserved newly generated identity values. The exercise found and fixed MySQL 1674 for adding an evaluated UUID default to a nonempty table: migration 004 now adds a nullable column, backfills UUIDs with row-logged DML, and only then enforces NOT NULL/default. Both source servers were already using ROW; disabling binlog was unnecessary. Rehearsal databases, accounts, credentials and copied data were removed afterward.

Production HTTPS checks with valid certificates pinned each entrance independently. A unique invitation-only test account uploaded one small file through each entrance. Read-only SQL verified each body existed only on its expected node and matched the expected SHA256, size and catalogue route. Cross-entrance session access, reads, retry replay/conflict, trash/restore, permanent deletion and delete replay passed. The backend reported the exact 20 GB quota and combined usage; all test file bytes, quota reservations and user gates were cleared by the end of CRUD checks. The test plan retains the temporary account through coordinated outage checks and removes it afterward.

These checks made no paid AI requests. They do not establish whole-server power-loss behavior or unrestricted-root disk guarantees. Failure-injection results and the final deployment owner’s outage report should be read within their stated scope.
