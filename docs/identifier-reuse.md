# Star Hub identifier reuse

This document describes the current Star Hub source as inspected on 14 November 2026. No identifier-allocation runtime or account CRUD was added by this audit. The source review does not establish the complete live database schema, all external administration procedures, or the absence of independently managed records.

- **Users:** The application uses numeric user IDs and a separate account generation. The reviewed account servlet provides login, logout, password changes and API-key management; it does not implement user registration or account deletion. The reviewed project deployment and maintenance scripts do not expose a production user-creation or deletion allocator. There is therefore no existing user-creation transaction to which a recycling allocator can be safely attached. Do not reset `AUTO_INCREMENT`, renumber accounts or assume a vacant user ID is safe to assign.
- **Files and trash:** New file records use randomly generated UUIDs. Moving a file to trash and restoring it retains the ID of that same file; this is restoration, not reassignment to another file. Permanent deletion does not feed a file-ID recycling pool. New files do not intentionally reuse deleted file IDs.
- **Chats:** New chat IDs are generated as UUIDs and are scoped by user ID in the conversation key. Deleting a chat does not make its ID available for deliberate reassignment to another chat.
- **Operations and protected identities:** API-key IDs, guest identities, provider/file operation IDs, durable receipts and payload identities use UUIDs or other bound identifiers. Their purpose includes authorization, idempotency and recovery. They are not placed into an identifier-reuse pool; do not reset or deliberately recycle them. A random UUID provides a very large namespace, not a mathematical guarantee that a collision is impossible.
- **Payload chunk indexes:** A chunk index is a local sequence within a distinct payload identity. A new payload can begin again at index zero because its parent payload ID is different; this is already scoped reuse, not the reuse of an old payload or operation ID.
- **Fixed system identities:** Singleton gates, coordinator sentinels and physical node identifiers have defined meanings. They are not vacant business IDs and must not be recycled as application records.

If a future release introduces account creation or deletion and ID reuse is still desired, design it around the actual deployed schema and all writers. It must create a fresh generation, verify and safely handle foreign keys **and references without foreign keys**, old sessions, file and quota records, API keys, unfinished transactions and retained operation receipts. An atomic database lock, uniqueness checks, rollback behavior and idempotent request handling must prevent concurrent assignment and stale requests from attaching old data to a new account. Test concurrency, rollback, retries, deletion and recreation, generation changes, old sessions and cross-account isolation against isolated synthetic data before deployment. If any old reference cannot be proven safe, do not reuse that ID.

The current assessment was a read-only source review. It did not call paid provider APIs, delete data, change production, or test a newly implemented reuse feature.
